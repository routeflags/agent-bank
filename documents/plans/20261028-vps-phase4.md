## Caddyfile の構造とドメイン未設定時の挙動

- サイトアドレスが `localhost` の場合、Caddy の自動 HTTPS は対象外となるため、
  **証明書の取得も HTTPS へのリダイレクトも行わず、ポート 80 を HTTP のまま提供する**。
  内部証明書の発行もしない。`APP_DOMAIN` が空のとき compose が `localhost` に読み替える
  ので、ドメイン未設定のまま `up -d caddy` しても証明書取得は発生しない。
- `APP_DOMAIN` に公開 FQDN を設定すると、Caddy が証明書を自動取得・更新し、
  HTTP → HTTPS リダイレクトを有効化する。Caddyfile の変更は不要。
- `/_health` を含む全リクエストは `web:3000` に転送する。`/_health` は Rack ミドルウェアが
  直接応答し（DB 到達時は 200、それ以外は 503）、SSL リダイレクトを回避しているため、
  内部は HTTP のままでよい（`always_use_ssl=true` でもヘルスチェックは壊れない）。

## 手順 A：ドメインが無い状態での起動確認（HTTP のみ）

VPS 上で実行する。

```bash
# 1. 環境変数を用意する（APP_DOMAIN は空のままにする）
cp .env.example .env
# .env を編集する。APP_DOMAIN は空行のまま。MYSQL_* / DATABASE_URL /
# secret_key_base 等の必須値を設定する。

# 2. 展開結果を確認する
[REDACTED]

# 3. caddy を含めて起動する（初回は build に親の承認が必要）
docker compose -f compose.production.yaml up -d caddy

# 4. HTTP で応答を確認する（HTTPS リダイレクトが起きないこと）
curl -s -o /dev/null -w "%{http_code}" http://localhost/
curl -s http://localhost/_health
# 期待値: 200（/_health は DB 到達時に OK、未到達時は 503）

# 5. セキュリティヘッダと圧縮を確認する
curl -sI http://localhost/ | grep -i -E "x-content-type-options|referrer-policy|content-encoding"
```

合格条件：HTTP 200 が返り、`https://` へのリダイレクト（301/308）が発生しないこと。
証明書の取得を試みた形跡がないこと（`docker compose logs caddy` に ACME エラーが出ないこと）。

## 手順 B：ドメイン取得後にやること

```bash
# 1. DNS A レコードを登録する（VPS の公開 IP を指す。AAAA も使う場合は同様に）
#    伝播を確認する：
dig +short <ドメイン>

# 2. .env にドメインを設定する（Rails の `domain` と Caddy の APP_DOMAIN を一致させる）
#    .env 内：
#      APP_DOMAIN=<ドメイン>
#      domain=<ドメイン>
#      always_use_ssl=true
#      sharetribe_mail_from_address=<本番ドメインの送信元>

# 3. caddy を再起動する（Caddyfile の変更は不要）
docker compose -f compose.production.yaml up -d caddy

# 4. 証明書の取得を確認する
docker compose logs caddy | grep -i -E "certificate|acme|tls"
curl -s -o /dev/null -w "%{http_code}" https://<ドメイン>/
curl -s http://<ドメイン>/_health -o /dev/null -w "%{http_code} %{redirect_url}\n"
# 期待値: https:// で 200、http:// は https:// へリダイレクト（301/308）
```

注意：DNS が伝播する前に caddy を FQDN で起動すると証明書取得に失敗し、
レート制限（Let's Encrypt）に達する恐れがある。`dig` で A レコードを確認してから起動すること。
失敗した場合はボリューム（`caddy_data`）を残したまま再試行すれば、取得済み証明書は再利用される。

## ロールバック

```bash
# caddy のみ停止する（web/worker/mysql/redis は継続できる）
docker compose -f compose.production.yaml stop caddy

# 構成ごと外す場合（証明書ボリュームは残る。作り直す場合は残し、破棄する場合のみ削除）：
docker compose -f compose.production.yaml rm -f caddy
# 証明書ボリュームを破棄する場合のみ（ドメイン変更等）：
# docker volume rm <プロジェクト名>_caddy_data <プロジェクト名>_caddy_config

# HTTP 公開に戻す場合：caddy 停止中は 80/443 が無応答になる。
# web は 127.0.0.1:3000 のままなので、外部公開は caddy 経由に限定され続ける。
```
