## バックアップの取得手順

```bash
# VPS 上のリポジトリ直下で実行
sudo bash script/db_backup.sh

# 保持世代の変更例（30 世代）
sudo KEEP=30 bash script/db_backup.sh
```

動作:

1. `docker compose -f compose.production.yaml exec -T mysql` 経由で `mysqldump` を実行。
   オプションは `--single-transaction --quick --routines`（稼働中の整合性を保つ。InnoDB 前提）。
2. 認証情報はコンテナ側の環境変数（`MYSQL_ROOT_PASSWORD`）を使い、ホストのコマンド履歴やログに出さない。
3. 出力先 `/var/backups/agent-bank/db/YYYYmmdd-HHMMSS.sql.gz`（ディレクトリは 700、ファイルは 600）。
4. 一時ファイル（先頭ドット付きで世代管理の対象外）に書き出し、`gzip -t` 検証後に rename。
   失敗時は非 0 で終了し、一時ファイルは trap で削除する。
5. 更新日時順に新しい方から `KEEP` 件（既定 14）を残し、古いものを削除する。

確認:

```bash
ls -lth /var/backups/agent-bank/db/ | head
 gzip -t /var/backups/agent-bank/db/<ファイル名> && echo OK
```

## cron 例（毎日 3:00）

JST 3:00（サーバーのタイムゾーンが UTC の場合は `TZ=Asia/Tokyo` を付けるか 18:00 UTC に読み替える）。
リポジトリの配置先は仮に `/opt/agent-bank` としている。実際の配置先に読み替えること。

```cron
# /etc/cron.d/agent-bank-db-backup（root 実行）
MAILTO=ops@example.com
0 3 * * * root /usr/bin/bash /opt/agent-bank/script/db_backup.sh >>/var/log/agent-bank-db-backup.log 2>&1
```

- 終了コード非 0 のみ通知したい場合は、`chronic`（moreutils）を使うか、ラッパーで失敗時に `mail` する。
  最低限、Phase 7 の運用監視でログの最終行とファイル更新時刻を監視すること（バックアップ失敗検知）。
- cron 登録後は翌朝に `/var/backups/agent-bank/db/` の更新とログを確認する。

## リストア手順（本番復元）

```bash
# VPS 上のリポジトリ直下で実行（対話実行。--yes は付けない）
sudo bash script/db_restore.sh /var/backups/agent-bank/db/20261028-030000.sql.gz
```

動作:

1. 復元対象 DB・復元元ファイルを表示し、確認プロンプトを出す（`--yes` / `-y` で省略可）。
2. 復元前に現行 DB を `pre-restore-YYYYmmdd-HHMMSS.sql.gz` に退避する（`db_backup.sh` に委譲）。
   退避に失敗したら復元に進まない。
3. `gzip -dc` → `mysql` サービスのパイプで復元する。
4. 復元後に以下を表示して検証する。いずれかの取得に失敗したら非 0 で終了する。
   - `information_schema` によるテーブル数
   - 代表 3 テーブルの行数（`listings` / `chat_sessions` / `wallets`）

復元後にアプリの疎通（ログイン、ペルソナ一覧、チャット送信）を確認し、問題があれば
退避した `pre-restore-*` ファイルで同手順により戻す。

## 検証環境での復元テスト手順（別 DB 名に復元して比較）

本番 DB を直接触らず、復元可能性を検証する手順。**初回バックアップ取得後に必ず実施する**。

```bash
# 1. 検証用 DB を作成（mysql サービス上で実行）
docker compose -f compose.production.yaml exec -T \
  -e "MYSQL_DATABASE=sharetribe_production" mysql sh -c \
  'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "CREATE DATABASE restore_test;"'

# 2. バックアップを検証用 DB に復元
zcat /var/backups/agent-bank/db/20261028-030000.sql.gz | docker compose -f compose.production.yaml exec -T \
  -e "MYSQL_DATABASE=restore_test" mysql sh -c \
  'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE"'

# 3. テーブル数・行数を本番と比較する（例）
for db in sharetribe_production restore_test; do
  docker compose -f compose.production.yaml exec -T -e "MYSQL_DATABASE=$db" mysql sh -c \
    'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -N -B "$MYSQL_DATABASE" -e "SELECT COUNT(*) FROM information_schema.TABLES WHERE TABLE_SCHEMA = DATABASE(); SELECT COUNT(*) FROM listings; SELECT COUNT(*) FROM chat_sessions; SELECT COUNT(*) FROM wallets;"'
done

# 4. 後片付け
docker compose -f compose.production.yaml exec -T \
  -e "MYSQL_DATABASE=sharetribe_production" mysql sh -c \
  'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "DROP DATABASE restore_test;"'
```

合格基準: テーブル数が一致し、3 テーブルの行数が本番と一致すること。
不一致の場合はバックアップ取得時のエラー・`gzip -t` 結果・ダンプサイズを確認する。

## 保持期間・保存先・ディスク容量の見積り

- 保存先: `/var/backups/agent-bank/db/`（VPS ローカル）。VPS 外部への転送は未実装（後述）。
- 保持期間: 既定 14 世代（日次取得で約 2 週間分）。`KEEP=` で変更可。
- 環境のディスク: 99G、使用 3.1G（Issue #99 記載値。Phase 1 実測時は 2.8G）。

見積り式（gzip 後の 1 世代を S とする）: 必要容量 ≒ S × (KEEP + 1)＋余裕。
`+1` は復元前退避（`pre-restore-*`）の 1 世代分。
`pre-restore-*` は `*.sql.gz` に一致するため世代管理の対象になるが、復元直後に古い世代を
押し出す可能性がある。退避ファイルを確実に残したい場合は復元後に別名保管すること。

DB サイズは本番稼働前のため未測定。実測コマンド:

```bash
# DB 全体の論理サイズ
docker compose -f compose.production.yaml exec -T mysql sh -c \
  'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -N -B -e "SELECT ROUND(SUM(data_length + index_length) / 1024 / 1024, 1) FROM information_schema.TABLES;"'

# 直近世代の実ファイルサイズ
du -h /var/backups/agent-bank/db/ | tail -1; ls -lh /var/backups/agent-bank/db/ | head -5
```

目安: DB 論理 100MB → gzip 後は 10〜30MB 程度が一般的。14 世代で 150〜450MB であり、
空き 90G 以上に対して十分に余裕がある。DB が 1GB を超える規模になったら世代数と外部転送を再検討する。

## Redis の扱い

- 現状: dev compose の `redis` サービスに volume も `appendonly` 等の永続化設定もない。
  Phase 3 の `compose.production.yaml` がこのまま踏襲されれば、Redis の内容はコンテナ再作成で失われる（揮発）。
- 影響評価:
  - Delayed::Job のキューは `delayed_jobs` テーブル（MySQL）に格納されるため、ジョブ自体は MySQL の
    バックアップで保全される。Redis 喪失でジョブが消えることはない。
  - 失われるのはキャッシュ・セッション等の一時データであり、再生成可能。ただしセッション断や
    一時的な性能低下は起こりうる。
- 要検討（Phase 3 / Phase 7 で決定）:
  1. 揮発を許容する場合は、その旨を運用方針として明記する（現状の推奨）。
  2. 永続化が必要な場合は、`redis:7-alpine` に named volume＋`command: ["redis-server", "--appendonly", "yes"]`
     を付け、RDB/AOF ファイルもバックアップ対象に加える。AOF がある場合の復旧方針（AOF リプレイ優先、
     破損時は `redis-check-aof`）は別途手順化が必要。
