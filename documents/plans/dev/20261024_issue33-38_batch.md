### #36 自分の出品に編集ボタンを出す
- 振る舞い: `GET /:locale/listings/:id` で `@listing.author == @current_user` のとき `.raku-cta-group` 内に `edit_listing_path(@listing)` への `a.raku-cta-btn.raku-cta-btn--ghost` を出す。文言は `t("listings.edit_links.edit_listing")` 流用。新規 locale キー追加なし。
  - 正常系: 出品者本人が自分の出品を開く → 編集ボタン表示 + 既存 CTA（利用する等）は維持。例: listing 22 を author 本人で表示。
  - 異常系: 他人の出品 → 編集ボタンなし・従来 CTA のみ。未ログイン → ログインボタンのみ・編集なし。
  - エッジ: `@current_user` が nil / author が nil のとき誤表示しない（`logged_in? && @listing.author == @current_user` ガード）。管理者だが author でない場合は出さない。
- 検証: 対象指定 request/view spec（author/他人/未ログインの3状態）+ 既存 listing 関連 spec の回帰。

### #37 アップロード済み画像が表示されない根本原因修正
- 根本原因（特定済み）: `39610c62e` のダークテーマ書き換えで `%script#image-frame-template` と `%script#image-thumbnail-template` が削除された。以降 `ST.imageCarousel` の `_.template($("#image-frame-template").html())` と `ST.thumbnailStripe` の `_.template($("#image-thumbnail-template").html())` が空で失敗し、サーバーが `:images_ok` を返しても JS 描画が空になる。`application.js` は `//= require image_carousel / thumbnail_stripe / listing_images` を維持しており配信自体は生きている。`ListingImageJsAdapter` の URL（`image.url(:thumb/:big)`）と `image_ready?` 分岐は正常。
- 振る舞い: `with_image_frame` が `:images_ok` のとき、カルーセル枠 `#listing-image-frame` + `#thumbnail-stripe` + 2つの `script[type="text/template"]` が出力され、`ST.listingImages(listingImages, currentImage)` が例外なく空でない `<img>` を描画する。
  - 正常系: `listing_images id=11（listing 22, image_downloaded=true, processing=false, error=nil）` → 詳細で big 画像 `<img src="/system/images/11/big/...">` が1枚以上描画される。2枚以上ならサムネイルも描画。
  - 異常系: `image_processing=true` → `:images_processing` で処理中文言。画像なし → プレースホルダー維持。
  - エッジ: 単一画像 → `thumbnail_stripe.js:37 if(elements.length < 2) container.hide()` でストライプ非表示だが本画像は表示。`params[:image]` 不正 → `listing_images.first.id` にフォールバック。
- 実装方針: 現行 `show.haml` の hero 内に旧テンプレ2つを復元（`39610c62e^` の内容を Raku 構造に合わせ `alt: @listing.title` 維持）。`listing_images.js`・`image_carousel.js`・`thumbnail_stripe.js` 本体は触らない。
- 検証: 静的 grep（テンプレIDの存在）+ サーバー側 request spec（`:images_ok` 時にテンプレ・`listingImages` JSON・big URL が含まれる）+ 可能ならヘッドレスで `#listing-image-frame img` の存在確認。DevTools 実機確認は人手依頼。

## 単位2: #34 ウォレットのチャージ有効化
- 方針（Issue に記録する）: 開発環境 = `dev_mode_topup?（Rails.env.development? && !stripe_key_configured?）` の擬似決済で実チャージ可能にする。本番 = Freemius または Stripe のキー投入後に有効化。キー未投入では「なぜ準備中か」を画面に明示する。実キー投入は承認事項のため実施しない。
- 振る舞い:
  - 正常系（開発）: `POST /api/v1/wallet_topup {amount_cents: 3000}` → `{client_secret, payment_intent_id: "dev_pi_*", dev_mode: true}`。続く `POST /api/v1/wallet_topup/confirm` → `Wallet#topup!` で残高加算・冪等（二重 confirm は `amount_credited: 0` + `既に処理済みです`）。フロントは `WalletTopupModal` の既存 Stripe フォールバック経路を壊さず dev_mode でも confirm する。ボタン文言は状態と一致（開発で利用可能なら「追加する」、不可なら理由付き「準備中」）。
  - 異常系: 金額範囲外（99 / 10001）→ 422。未ログイン → 401。`payment_intent_id` なし → 400。不正 dev_pi（改ざん・他人の uid）→ 403/422。他人の wallet を指す payload → 403 または 404。`WalletTopupController` の既存分岐（Freemius 優先・Stripe フォールバック・dev 優先）は順序を変えない。
  - エッジ: 同一 dev_pi の二重 confirm → 残高二重加算なし。`stripe_key_configured?` が true の開発環境 → dev 経路に入らず Stripe 経路。テスト環境 → `dev_mode_topup?` は false（既存仕様維持）。本番キー未設定 → 「決済未設定」の理由表示に倒す。
- 実装方針: バックエンド分岐は原則触らない。フロント `ChatPanelApp.js` の固定 `t('wallet_add_preparing')` を、利用可否に応じた文言+理由表示に変える（文言は `lamprey.chat.*` に追加し `ChatPanelHelper#chat_panel_i18n` 経由。直書き禁止）。利用可否の判定は新規の軽量 status 取得または既存 balance 取得の拡張のいずれか最小差分で、方針コメントを Issue に残す。
- 検証: `spec/requests/api/v1/wallet_topup*`・`spec/services/*wallet*` 等の影響範囲を対象指定で実行 + isolated 再実行 + 変更前後失敗集合比較で新規0件。開発 MySQL での実チャージ動作は request spec の dev 経路で確認。
